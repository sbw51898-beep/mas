# DeepSeek 多智能体认知治理正式试跑设计

日期：2026-07-27

## 1. 研究目的

本阶段建立一套可审计的正式实验协议，并使用 DeepSeek API 对一道隐藏信息题进行工程试跑。目标不是凭一道题证明某种治理机制有效，而是验证：

1. 三种发言机制能否在相同模型、相同任务和相同调用预算下运行；
2. 每名 Agent 的私有信息、可见历史、概率信念和发言轨迹能否完整记录；
3. 任务结果指标、信念过程指标和探索性社会热力学代理量能否按预先定义计算；
4. 后续扩样实验是否具备可重复、可比较和可审计的基础。

本设计独立实现，不使用贺同学的代码。贺文仅作为待复核的研究对象和术语来源。

## 2. 研究问题和结论边界

### 2.1 工程问题

- DeepSeek V4 Flash 非思考模式能否稳定返回符合约束的概率分布；
- 三种机制是否各自完成 9 次有效模型调用；
- 日志能否证明每次调用实际看到了哪些信息。

### 2.2 探索性研究问题

- 公开讨论是否提高隐藏信息的汇总程度；
- 固定轮流和动态发言是否产生不同的信息共享、答案翻转和分歧轨迹；
- 高共识是否可能与错误答案同时出现；
- 探索性代理量 `(R, mean_b, T_proxy, H_proxy, F_proxy)` 是否随讨论呈现可解释变化。

### 2.3 不允许作出的结论

单题单次运行不得用于声称：

- 动态发言优于固定轮流或独立思考；
- 共识与正确性存在稳定相关关系；
- `T_proxy` 是真实温度，或 `F_proxy` 是真实 Helmholtz 自由能；
- 已复现贺文的统计结果；
- 已验证 MAST 检测器的真阳性率或假阳性率。

## 3. 模型与接口

- 服务：DeepSeek 官方 API；
- OpenAI-compatible Base URL：`https://api.deepseek.com`；
- 模型：`deepseek-v4-flash`；
- 思考模式：显式设置 `thinking.type=disabled`；
- 采样温度：`0`；
- 流式输出：关闭；
- 输出：JSON；
- 密钥：仅从环境变量读取；
- 版本记录：保存请求时间、模型名、SDK版本、MAF版本和可获得的请求/用量元数据。

DeepSeek V4 默认启用思考模式，因此实验调用必须显式禁用。官方依据：

- https://api-docs.deepseek.com/guides/thinking_mode
- https://api-docs.deepseek.com/api/create-chat-completion

本试跑使用 DeepSeek V4 Flash，而贺文报告使用 DeepSeek V3。两者不是同一模型，本试跑不能被表述为对贺文结果的直接复制。

## 4. 隐藏信息任务

### 4.1 公共题目

某机构需要从 A、B、C、D 四家供应商中选择一家。综合得分为：

```text
总分 = 0.40 × 可靠性 + 0.35 × 安全性 + 0.25 × 成本优势
```

所有维度均为 0 到 100 分，分数越高越好。所有 Agent 都知道权重、候选项和计算规则，但每名 Agent 初始只知道一个维度的数据。

### 4.2 私有信息

| Agent | 专业角色 | 私有维度 | A | B | C | D | 单维度最高 |
|---|---|---:|---:|---:|---:|---:|---|
| agent-a | 可靠性分析员 | 可靠性 | 95 | 75 | 85 | 65 | A |
| agent-b | 安全审计员 | 安全性 | 55 | 95 | 85 | 70 | B |
| agent-c | 成本分析员 | 成本优势 | 75 | 60 | 90 | 100 | D |

Agent 不得看到其他 Agent 的私有数据，除非数据在公开发言中被说出。

### 4.3 标准答案

汇总全部信息后的真实得分：

| 供应商 | 加权总分 |
|---|---:|
| A | 76.00 |
| B | 78.25 |
| C | 86.25 |
| D | 75.50 |

标准答案为 C。每名 Agent 单看自己的维度时分别倾向 A、B、D；正确选择 C 需要跨 Agent 汇总信息。

### 4.4 防止答案泄漏

- 标准答案和完整总表只进入评估器，不进入 Agent 提示词；
- Agent 提示词不包含其他角色的私有数值；
- 运行时选择器不得读取标准答案；
- 日志分别保存“系统拥有的信息”和“Agent 实际可见的信息”。

## 5. 结构化信念输出

每次 Agent 发言必须返回：

```json
{
  "answer": "B",
  "probabilities": {
    "A": 0.10,
    "B": 0.70,
    "C": 0.15,
    "D": 0.05
  },
  "reasoning": "简要说明依据，以及使用了哪些公开信息"
}
```

约束：

- `answer` 必须是 A、B、C、D 之一；
- `probabilities` 必须恰好包含 A、B、C、D；
- 每个概率必须在 `[0,1]`；
- 概率和与 1 的偏差不得超过 0.01；
- `answer` 必须等于最高概率选项；
- 并列时按 A、B、C、D 的预先顺序选择，并记录并列标记；
- `confidence_i = max_k p_i(k)`，不再接受独立自报的置信度。

浮点舍入误差在容差内时由程序归一化。超出容差、字段缺失或答案与概率矛盾时，允许一次格式修复重试；第二次仍失败则该调用无效。

## 6. `b_i` 的操作性定义

四选一任务没有天然的一维左右轴，因此不得把 A、B、C、D 直接编码为 `[-1,1]`。系统首先保存完整概率向量：

```text
p_i = [p_i(A), p_i(B), p_i(C), p_i(D)]
```

对一个明确指定的参照选项 `k`，定义：

```text
b_i(k) = 2 × p_i(k) - 1
```

含义：

- `b_i=-1`：完全否定参照选项；
- `b_i=0`：对参照选项为五五开；
- `b_i=+1`：完全支持参照选项。

### 6.1 运行时信念

在已有三名 Agent 的初始概率后，令：

```text
k_t = argmax_k mean_i p_i(k)
b_i_runtime(t) = 2 × p_i(k_t) - 1
```

`k_t` 仅由当时已有的 Agent 输出决定，不使用标准答案。若群体平均概率并列，按 A、B、C、D 的预先顺序选择并记录并列。

第一轮尚未收齐三名 Agent 的初始输出时，只记录概率向量，不计算群体运行时 `b_i`。

### 6.2 评估信念

实验结束后，以标准答案 `y*` 为参照：

```text
b_i_eval = 2 × p_i(y*) - 1
```

`b_i_eval` 只能用于事后评估，禁止进入 Agent 提示词、发言选择和终止判断。

## 7. 指标定义

令 Agent 数量 `N=3`，选项数量 `K=4`。最终状态使用每名 Agent 最后一次有效响应。

### 7.1 第一层：任务结果指标

#### 概率池化答案

```text
p_group(k) = mean_i p_i(k)
pooled_answer = argmax_k p_group(k)
```

并列按 A、B、C、D 的预先顺序处理并记录。`pooled_answer` 是预先指定的主要集体答案。

#### 多数票答案

根据各 Agent 的最终 `answer` 计算多数票。三者全不同时按预先顺序处理并记录。多数票作为次要集体答案，用于检查它与概率池化是否一致。

#### 正确率

```text
accuracy = 1 if pooled_answer == correct_answer else 0
```

#### 多数集中度

```text
majority_share = max_k count(answer_i=k) / N
```

旧名称 `consensus_rate` 更名为 `majority_share`，因为 `2/3` 只能表示多数集中，不等于全体共识。

#### 全体一致

```text
unanimity = all final answers are identical
```

#### 错误共识

```text
wrong_consensus = unanimity and pooled_answer != correct_answer
```

#### 答案翻转率

```text
flip_rate = changed answer transitions / comparable answer transitions
```

### 7.2 第二层：信念和讨论过程指标

#### 答案熵

令 `q(k)` 为最终选择选项 `k` 的 Agent 比例：

```text
answer_entropy =
  -sum_k q(k) log q(k) / log(min(K,N))
```

只有正概率项进入求和。使用 `log(min(K,N))` 是因为 3 名 Agent 最多只能占据 3 个非空选项。

#### 概率分歧

令 `p_bar` 为 Agent 概率向量的均值：

```text
JS_disagreement =
  [H(p_bar) - mean_i H(p_i)] / log(min(K,N))
```

该广义 Jensen-Shannon 分歧归一化到 `[0,1]` 的可达范围。

#### 两两答案分歧

```text
pairwise_disagreement =
  不同答案的 Agent 对数 / 全部 Agent 对数
```

#### 发言占比

```text
speaker_share(i) = agent_i 发言次数 / 总发言次数
```

#### 多分类 Brier 分数

```text
Brier_i = sum_k [p_i(k) - 1(k=y*)]^2
group_Brier = mean_i Brier_i
```

数值越低表示概率预测越好。它是事后评估指标，不进入运行时选择器。

### 7.3 第三层：探索性社会热力学代理量

给定同一个参照选项 `k`：

```text
b_i = 2 p_i(k) - 1
theta_i = (pi/2) b_i
mean_b = mean_i b_i
R = |mean_i exp(j theta_i)|
T_proxy = population_std(b)
```

将 `b_i` 放入 5 个固定等宽区间，得到区间概率 `r_m`：

```text
H_proxy = -sum_m r_m log(r_m) / log(min(5,N))
F_proxy = (1-R) + T_proxy × H_proxy
```

解释限制：

- `mean_b` 表示总体支持还是反对参照选项；
- `R` 只表示方向对齐程度，不表示方向正确；
- `R` 必须和 `mean_b` 同时报告；
- `T_proxy` 是信念离散度代理，不直接称为温度；
- `H_proxy` 是三名 Agent 在信念区间上的离散熵；
- `F_proxy` 是启发式无序综合量，不直接称为 Helmholtz 自由能；
- 第三层指标在完成跨任务验证前不得用于控制正式结论。

## 8. 三种等预算机制

每种机制固定 9 次模型调用。三种机制使用相同模型、题目、角色私有信息、输出约束和最大输出长度。

### 8.1 公共初始阶段

固定先调用 agent-a、agent-b、agent-c 各一次，但三次请求互相不可见。三次完成后：

- 独立模式不公开这些响应；
- 固定轮流和动态模式把三条初始响应同时加入公共历史；
- 日志记录三次初始请求的可见历史为空。

### 8.2 独立自省模式

- 每名 Agent 额外自省两次；
- Agent 只能看到题目、自己的私有信息和自己的先前响应；
- Agent 永远看不到其他 Agent 的消息；
- 总调用数：`3 + 3×2 = 9`。

该模式是等预算的“无跨 Agent 信息交换”基线。

### 8.3 固定轮流模式

- 公共初始阶段后，按照 A、B、C 的顺序讨论两轮；
- 每次发言可见此前所有公共响应；
- 总调用数：`3 + 3×2 = 9`。

### 8.4 动态发言模式

- 公共初始阶段后，剩余 6 次发言由确定性选择分数决定；
- 所有候选 Agent 每一步都计算分数；
- 只选择最高分 Agent 发言；
- 分数相同时按 Agent ID 升序；
- 总调用数：`3 + 6 = 9`。

第一版动态分数：

```text
dynamic_score_i =
    0.45 × disagreement_i
  + 0.30 × waiting_i
  + 0.25 × uncertainty_i
```

其中：

```text
disagreement_i = normalized_JS(p_i, p_bar)
waiting_i = 该 Agent 距上次发言的步数 / 当前最大等待步数
uncertainty_i = 1 - max_k p_i(k)
```

该三因子公式是工程基线，不冒充贺文的五因子公式，也不宣称权重最优。每一步保存所有候选分量、总分和最终选择。

## 9. 信息共享与 MAST 对照记录

本试跑只生成可供人工核查的信号，不宣称已验证自动检测器。

### FM-2.4 信息隐瞒候选信号

检查每名 Agent 是否在公开发言中披露其私有维度的关键数值。未披露仅标记为候选现象，不能自动判定失败，因为沉默可能与发言机会有关。

### FM-2.5 输入忽视候选信号

检查 Agent 后续推理是否引用或数值使用了公共历史中已披露的信息。只依据文本关键词不得直接判定“忽视”，需结合最终计算和人工复核。

### FM-2.6 推理-行为不匹配候选信号

检查 `answer` 是否与 `probabilities` 的最大项一致，以及推理文本推荐对象是否与结构化答案一致。结构化矛盾属于可自动检查项；语义矛盾只作为人工审计项。

## 10. 日志和安全

每个“题目 × 模式”生成一条 JSONL 结果，必须包含：

- 运行 ID、时间和实验配置；
- 模型、MAF、OpenAI SDK、Python和项目版本；
- 公共题目和标准答案；
- Agent 角色和私有信息；
- 每次请求实际可见的消息 ID；
- 每次用户提示；
- 原始模型输出；
- 解析后的概率向量、答案、推理和置信度；
- 格式修复次数；
- 动态选择的全部候选分数；
- 每一步 `p_i`、运行时 `b_i` 和代理量；
- 最终两种集体答案和全部指标；
- token 用量、请求标识和错误信息（若客户端提供）。

日志不得包含：

- API Key；
- Authorization Header；
- 完整环境变量；
- 任何名称含 `api_key`、`authorization`、`token` 或 `secret` 的未脱敏字段。

## 11. 错误处理

1. 先执行一次不计入实验的连通性请求；
2. 连通性通过后才运行 27 次实验调用；
3. JSON、字段或概率校验失败时允许一次格式修复重试；
4. API请求失败时记录错误，不伪造响应；
5. 任一模式少于 9 次有效调用，该模式标记为不完整；
6. 任一模式不完整时，本次试跑不作三模式比较；
7. 输出采用逐条追加，防止中途故障丢失已完成结果；
8. 失败重跑写入新文件，不覆盖原始失败轨迹。

格式修复请求不计入 9 次讨论预算，但必须单独记录实际 API 调用数和额外成本。

## 12. 测试策略

在真实调用前，使用测试驱动方式覆盖：

1. 四项概率的字段、范围、和、最大项校验；
2. 轻微浮点误差归一化和明显错误拒绝；
3. `b_i_runtime` 与 `b_i_eval` 不混用；
4. 多数集中度、全体一致、错误共识、答案熵、JS分歧和Brier分数；
5. `(mean_b, R, T_proxy, H_proxy, F_proxy)` 的边界情况；
6. 三种模式均恰好 9 次有效讨论调用；
7. 初始三次调用互相不可见；
8. 独立模式只看自己的历史；
9. 固定轮流和动态模式看到正确的公共历史；
10. DeepSeek请求显式包含 `thinking=disabled`；
11. 日志递归脱敏；
12. 离线确定性提供程序仍可完成全部测试。

## 13. 真实试跑步骤

1. 用户在本机安全配置 DeepSeek API Key，不把密钥发送到聊天；
2. 配置：

   ```powershell
   $env:OPENAI_BASE_URL="https://api.deepseek.com"
   $env:OPENAI_CHAT_COMPLETION_MODEL="deepseek-v4-flash"
   ```

3. 执行连通性检查；
4. 检查返回模型名、JSON格式和非思考模式；
5. 用新输出文件运行一道隐藏信息题的三种模式；
6. 验证每种模式 9 次有效调用；
7. 搜索输出确认不存在密钥；
8. 生成单题审计摘要；
9. 把“工程观察”和“研究结论”分栏报告。

## 14. 验收标准

- 全部原有和新增自动测试通过；
- 离线运行不需要API Key；
- 三种模式各完成9次有效调用，共生成3条模式结果；
- 每次调用的私有信息和可见历史可审计；
- 完整概率向量和三层指标可计算；
- `proxy` 命名和结论限制保留在输出与报告中；
- 输出中没有API Key或Authorization信息；
- 试跑报告不根据单题结果宣称机制优劣。

## 15. 后续正式扩样

单题试跑通过后，再单独设计预注册式扩样：

- 增加任务数量和难度层级；
- 每个条件使用多个独立重复；
- 比较多个模型；
- 加入五因子发言公式及逐因子消融；
- 使用置换检验、效应量和多重比较校正；
- 对 MAST 候选信号进行人工双人标注；
- 验证探索性代理量能否在基础指标之外预测错误共识或任务失败。
