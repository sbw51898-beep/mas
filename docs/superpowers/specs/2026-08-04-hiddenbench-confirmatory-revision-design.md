# HiddenBench 确认性修订实验设计

## 1. 目标

在保留 2026-08-02 至 2026-08-03 探索性实验及其原始报告的前提下，新增一套可直接回应彭老师质疑的确认性实验，解决以下问题：

1. 题目与论文对标关系错误：确认性题目固定为 HiddenBench ID1、ID2、ID3，即官方 `benchmark_short.json` 中的三道论文验证题。
2. 披露率口径过粗：从 Agent 级信息包二元判断改为原子事实覆盖率。
3. 提前停止证据不足：在同一条完整 60 条讨论轨迹中加入不可见的逐轮影子投票，评估假设停止点与最终结果是否一致。
4. 单智能体对照表述不公平：同时报告局部信息单智能体、完整信息单智能体和多智能体组，不再把不同系统信息量包装成同一设定。
5. 代码版本无法严格还原：正式实验必须在干净且已提交的工作树上运行，记录的 commit 必须对应真实运行代码。
6. 公开复现不完整：配置、代码、摘要、门禁和哈希进入 Git；大体积原始数据通过公开 release 资产提供。

本确认性实验不删除或覆盖旧数据。ID5、ID7、ID25 保留为探索性困难案例，只在报告的历史结果或补充分析中出现，不再称为论文三道手工题。

## 2. 实验问题

确认性实验回答四个问题：

1. 在论文明确公开的三道验证题上，DeepSeek V4 Flash 使用 Microsoft Agent Framework 时，与官方 GPT-4.1 结果有何差异？
2. MAF 动态发言、固定轮转、Reveal-All 和 Structured 协议在相同任务、相同模型、相同信息分配下表现如何？
3. 私有信息中的多少原子事实真正由信息拥有者公开，披露后是否被正确使用？
4. 如果连续两轮出现相同的全体一致投票，在该轮停止是否会改变同一条完整讨论最终得到的答案？

## 3. 题目与模型

### 3.1 确认性题目

- ID1：`evacuation_west_city`
- ID2：`evacuation_north_hill`
- ID3：`evacuation_east_town`

题目来源必须是官方 HiddenBench `benchmark_short.json`。运行前记录数据文件 SHA-256；门禁验证三道题的名称、选项、正确答案和私有信息与官方快照一致。

### 3.2 模型

- 本地确认性运行：`deepseek-v4-flash`
- 温度：`0`
- thinking：`disabled`
- 重复次数：每题每条件 10 次
- 官方对照：下载作者公开的 GPT-4.1 逐题结果并独立重算，不把官方结果冒充本地 Microsoft Agent Framework 复现。

如果以后获得可用的 OpenAI API key，可在同一冻结协议上增加本地 GPT-4.1 条件；它不是本轮完成的前置条件。

## 4. 条件矩阵

确认性矩阵包含七个条件：

1. `fixed-60`：固定轮转 15 轮，共 60 条公开发言。
2. `dynamic-60`：MAF 五因子动态发言，共 60 条公开发言；无额外 selector LLM 调用。
3. `fixed-reveal-all`：固定轮转 60 条；第一轮机械附加该 Agent 的全部私有事实。
4. `dynamic-reveal-all`：MAF 动态 60 条；每个 Agent 第一次发言机械附加其全部私有事实。
5. `structured-12`：论文 Exchange 2 轮加 Decide 1 pass，共 12 条公开消息，之后独立投票。
6. `fixed-12`：固定轮转 3 轮，共 12 条公开发言，作为 Structured 的同预算基线。
7. `single-local`：单智能体仅获得 shared information 加一份 private information，作为局部信息下限。

每个多智能体运行同时保留四个 `full_profile` 独立投票，用作完整信息单智能体上限。报告将明确：`single-local` 与多智能体组的系统总信息量不同，不能用于证明多智能体普遍优于单智能体。

总规模为 7 条件 × 3 题 × 10 次 = 210 次确认性运行。API 请求数从每条运行记录的 `provider_metadata.api_requests` 确定性求和，不再手工估算。

## 5. 配对与可比性

同一 `(task_id, repetition)` 的所有条件必须使用：

- 相同的 `pair_seed`；
- 相同的私有信息分配；
- 相同的任务数据哈希；
- 相同模型配置。

DeepSeek 服务端不接收本实验 seed，因此 seed 只冻结信息分配，不宣称冻结模型输出。`temperature=0` 也不等于服务端完全确定。十次重复描述的是相同配置下的服务端非确定性和对话演化差异。

## 6. 原子事实披露率

### 6.1 原子事实定义

每个 Agent 的 private information 在运行前拆分为一组可独立判定真假的原子事实：

- 普通自然语言句子：以任务数据中的单条 private information 为最小原子；只有包含明显并列且可独立判断的多个断言时才进一步拆分。
- 字母表、候选人属性列表等结构化包：每个“对象—属性—取值”三元组是一条原子事实。
- 拆分结果写入运行配置快照并计算哈希；审计模型不得自行改变原子事实数量。

### 6.2 披露判定

对每条原子事实，审计器只查看：

- 原子事实文本；
- 信息拥有者 ID；
- 该拥有者的公开发言及消息 ID。

判为披露必须满足：拥有者说出原事实或保留其决策关键含义的忠实转述，并给出可校验的消息 ID 和连续原文引句。非拥有者猜测、极性颠倒、明显弱化或不在拥有者信息中的内容不算披露。

单次运行的原子披露率为：

`已披露原子事实数 / 全部私有原子事实数`

同时保留旧的信息包披露率作为历史指标，但不得与原子披露率混称。

### 6.3 质量控制

- Reveal-All 条件的原子披露率必须为 100%，否则门禁失败。
- 所有“披露”判断必须通过消息 ID、拥有者和原文连续子串校验。
- 生成一份不显示既有标签的盲审表；独立模型结果只标注为模型辅助复核，真人签核后才能报告人工精确率和召回率。

## 7. 同轨迹影子投票与提前停止

### 7.1 设计

对 `fixed-60` 条件，在每一轮四名 Agent 发言结束后执行四次影子投票。影子投票：

- 使用截至当前轮的公开消息；
- 不显示给讨论 Agent；
- 不写入后续讨论 prompt；
- 不改变后续发言顺序；
- 单独记录为 `shadow_votes`，不计入 60 条公开发言预算。

讨论仍完整运行 15 轮。这样可以在同一条对话轨迹上比较“假设提前停止”与完整 60 条讨论的最终投票，不再把不同重跑误称为同轨迹截断。

### 7.2 停止规则

候选停止点为首次满足以下条件的轮次：

1. 当前轮四个影子投票全体一致；
2. 前一轮四个影子投票也全体一致；
3. 两轮的一致答案完全相同。

### 7.3 指标

- 可停止覆盖率：30 个 `fixed-60` 运行中出现候选停止点的比例。
- 假设停止一致率：候选停止答案与第 15 轮后四个最终投票是否完全一致。
- 正确性变化：候选停止答案与最终多数答案各自是否正确。
- 平均节省发言数：`60 - 4 × 停止轮次`。
- 反例清单：所有候选停止答案与最终结果不一致的运行逐条列出。

只有当所有候选停止运行均与最终结果一致时，才能写“本样本未观察到提前停止翻转”；不得写成一般性的“提前停止是安全的”。

## 8. 官方 GPT-4.1 对标

从作者官方公开结果中下载并保存：

- 三道验证题 baseline 结果；
- 三道验证题 Reveal-All 结果；
- 其他确实公开且能确定题目映射的逐题干预结果。

对每个文件验证来源 URL、字节数和 SHA-256，使用本项目评分器重算：

- 票平均正确率；
- 多数正确率；
- 全体正确率；
- 错误共识率。

若 Structured 逐题文件未公开，报告明确写“只有 18 题聚合值，没有可核验的逐题文件”，不得虚构或推断。

## 9. 版本冻结与公开复现

### 9.1 运行前门禁

正式模型调用前必须：

1. `git status --porcelain` 为空；
2. 当前分支非 detached HEAD；
3. `frozen_code_commit` 已包含本轮协议和测试；
4. 当前 `HEAD` 是只修改确认性配置的冻结提交，且其父提交等于 `frozen_code_commit`；
5. `frozen_code_commit..HEAD` 之间的 `src/` 与 `tests/` 无差异。

`current_git_commit()` 增加工作区 dirty 检测；正式模式发现未提交改动时直接失败。运行记录同时保存当前运行提交 `run_commit=HEAD` 和运行时代码提交 `frozen_code_commit=HEAD^`，避免配置文件自引用哈希。

### 9.2 公开产物

Git 中保存：

- 配置；
- 代码和测试；
- 报告生成器；
- CSV/JSON 摘要；
- 门禁文件；
- SHA-256 manifest；
- 新 Word 报告。

大体积原始 JSONL、trace 和审计记录打包为压缩文件，作为 GitHub Release 资产公开。报告写入固定 commit URL、release URL 和每个资产哈希。

## 11. 测试与验收

### 11.1 代码测试

- dirty 工作树拒绝正式运行；clean 工作树允许运行。
- 原子事实拆分稳定、可哈希、无空原子。
- Reveal-All 每个原子事实都有拥有者证据且披露率为 100%。
- 影子投票不进入后续公开消息和 Agent prompt。
- 停止规则只在连续两轮相同全体一致时触发。
- 同题同重复的条件拥有相同 seed 和 assignment fingerprint。
- 七条件 × 三题 × 十次矩阵完整且无重复键。
- API 请求数由原始 provider metadata 汇总。
- 官方结果评分能够从公开 JSON 独立重算。

### 11.2 数据门禁

任何以下情况都会阻止报告生成：

- 缺少运行或重复键；
- 数据哈希不匹配；
- 代码 commit 不匹配或工作树 dirty；
- Reveal-All 原子披露率不是 100%；
- 披露证据消息不存在、非拥有者发言或引句不是原文子串；
- 影子投票轮次缺失；
- 官方结果来源或哈希缺失。

### 11.3 文档验收

- Word 包结构可打开；
- 表格列宽、标题层级和页码结构通过检查；
- 若 LibreOffice 可用，必须渲染全部页面并逐页检查；若不可用，报告交付时明确说明未完成本机视觉渲染门禁。
- 报告中的每个总数均能由原始摘要确定性回算。
